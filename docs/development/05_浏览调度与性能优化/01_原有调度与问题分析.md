# 01 原有调度与问题分析

阶段 2.3 的 `FileManagerApp` 用同一个 `disk` 执行器运行目录读取、搜索、预览、地址子菜单、目录树分支、命令准备和正式写入。`activeTask` 既是任务槽，也控制多数主窗控件。写入任务在文件系统操作结束后才释放这个槽。后台预览虽然有独立的 `previewTask` 引用，实际数据读取也在同一队列。原生属性窗和最近修改索引另开虚拟线程。 [阶段 2.3 交互](../04_文件操作引擎/04_JavaFX交互与任务调度.md) · [原始实现](https://github.com/hrao233/Java-/blob/996c839d02462677e06c98d849543823bd9edaf0/src/main/java/edu/files/FileManagerApp.java)

在真实 JavaFX 用例中，通过锁存器把 48 MiB 本地 NTFS 复制停在已报告字节的 `CopyFileExW` 回调。基线阶段两次 Maven 验证正常。加入新验收断言后，真实地址栏编辑按钮仍显示禁用，断言失败。独立性能夹具还向同一磁盘队列提交仅记录时间的任务，证实它在持有复制停点的固定观察窗口内没有运行。因此解除控件禁用后，旧队列仍会阻塞导航。 [复现用例](../../../src/test/java/edu/files/JavaFxFileOperationsTest.java) · [桌面性能夹具](../../../src/test/java/edu/files/Phase24FxBenchmark.java)

| 原入口 | 原调度和归属 | 具体影响 |
| --- | --- | --- |
| 地址、导航、历史、刷新 | 地址可能先检查类型，再启动名单读取。列表完成后提交位置和历史 | 请求空闲前其它导航被挡在控件或入口，缺少同时存在的请求归属。 |
| 搜索与图库 | 同一 `activeTask` 标记为可取消 | 取消状态也影响写入、导航和其它控件。 |
| 预览与属性 | 文本读取进入 `disk`，图片请求交给 JavaFX，属性 Shell 另开线程 | 预览槽与页面顺序不同，属性窗口数量缺少共同的调度边界。 |
| 目录树与地址子菜单 | 节点异步展开走 `disk` | 写入期间这些只读操作排队。 |
| 写入与任务窗 | 写入由单线程执行，快照由 JavaFX 定时读取 | 任务可取消，主窗只读请求被共享槽阻塞。 |
| 写后更新与关闭 | `afterWrite` 通常重新读取完成当时的页面。退出根据全局槽决定是否中断 | 并发导航后，需要以具体目录依赖安排刷新，并区分可丢弃读取与已提交写入。 |

请求协调必须同时回答当前归属、提交顺序和写后依赖。执行器解决排队，只有提交端能决定迟到的结果是否还对界面有效。 [新架构](02_浏览请求与文件任务架构.md)
