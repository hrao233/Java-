# 05 下一阶段架构候选

本阶段已经把每项文件变更与结果接到同一处。后续可以在现有 `FileChanges` 上补足请求、验证、执行与回执，继续让 JavaFX 负责确认、禁用和刷新，让 `LocalFiles` 保持可独立调用。无需为此先拆窗口、导航或视图。见 [当前代码](../../../src/main/java/edu/files/FileChanges.java) 和 [原重构候选](../../audit/08_代码质量与技术债务.md)。

| 候选 | 实际增加的保证 | 成本和适用场景 |
| --- | --- | --- |
| 在现有协调器补对象凭据与明确回执 | 同一批用一致的结果描述，错误触发可重复测试。Java 平台没有身份时保守拒绝或确认路径 | 改动较小，可继续服务单窗口。在 Windows 公共 NIO 上不能为可靠自动撤回提供所需的身份 |
| 增加 Windows 属性与句柄适配，逐项启用 | NTFS 上可检测典型替代。用同一打开的句柄设计移动/改名执行与校验，可缩小对象被调换的窗口 | 需要决定 JNA、原生组件或 Java 外部函数方案。Java 21 的 FFM 仍为预览，选型会影响发布。属性查询子进程适合实验，放入每项操作的热路径有成本与退出管理问题 |
| 为特定逆操作设计隔离和恢复 | 可以把明确选中的结果保留在可恢复位置，并为可支持的逆转提供证据 | 需要空间、权限、生命周期和失败恢复。对用户后续改写目录进行批量逆转仍要求严谨的内容与对象契约 |

建议先只定义 `OperationRequest → VerifiedSource → OperationReceipt` 在当前入口的最小契约。回执记录实际目标、是否写入、证据不足的原因及可提供的逆操作。用一个正式适配器或测试替身验证 `Path` 和卷处理。只在实现能够证明平台特性后，在支持的文件系统启用已验证的逆操作。该方案不需要改多级撤销、持久数据库或跨卷树协议。见 [身份实验](04_文件身份机制调查与设计.md)。

仍需项目维护者决定的取舍有三项。

1. **哪些环境优先支持。** 可以只为本机 NTFS 引入更强机制，网络、WSL、重解析对象保留安全限制。跨提供者行为一致则要接受更大的迁移和测试成本。
2. **身份不明时的前向动作。** 现阶段允许明确同意操作当前路径。后续可以为移动、重命名、回收采用重新选择或拒绝，为复制保留确认，以平衡便利性与误操作成本。
3. **复制与新建的撤销承诺。** 维持安全停用，或在有可验证身份和恢复语义的范围内恢复部分能力。目录递归撤销需要单独定义内容验证、并发变化和恢复能力。

下一阶段的验收应包含键可取得/不可取得的两种路径、父目录被替换、硬链接名称区分、同名等字节替换、未知操作后禁止无条件重试，以及 NTFS 句柄方案在竞争条件下的观测。相关前提和未验证项见 [测试与变更记录](06_测试与变更记录.md)。
