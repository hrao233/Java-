# 03 批量操作结果修复

原 `processChanges` 在 `IOException` 时返回已完成前缀。JDK Desktop 也可能因目标不再存在抛 `IllegalArgumentException`，让 Task 直接失败。此时此前的磁盘写入已经发生，界面层拿不到前缀。阶段基线使用假回收站重现了这一点。见 [原审查 F04](../../audit/06_文件操作与数据安全.md) 和 [基线测试记录](06_测试与变更记录.md)。

| 每项状态 | 何时记录 | 应用行为 |
| --- | --- | --- |
| 已写入 `APPLIED` | 操作返回成功 | 记实际写入、该项对应的逆操作或拒绝理由 |
| 无需更改 `UNCHANGED` | 同目录移动或同名无变化 | 算已处理，剪切可移除这项，没有逆操作 |
| 失败 `FAILED` | 前置检查拒绝、同名冲突等 | 保留原因，停止批次，本项及后续剪切条目保留 |
| 结果未知 `UNKNOWN` | 进入系统写入后收到不确定失败，例如回收 API 异常或未报告成功 | 仅读对应路径属性并报告检查时状态，停止。保留该剪切项，且不根据猜测创建逆操作 |
| 未执行 `NOT_RUN` | 排在失败或未知项之后 | 保留用户请求 |
| 已拒绝撤销 `REFUSED` | 自动撤销因安全策略禁用 | 给出原因，继续处理其它逆操作 |

`FileChanges.execute` 返回与输入顺序一致的每项结果，逆操作从成功项倒序生成。`Outcome.remainingCut` 按真正完成的前缀更新剪切队列。`FileManagerApp.afterWrite` 用成功结果记录父目录更改，在有写入、失败或未知时重读。未知也会触发侧栏刷新。错误提示保留原因，状态栏同时显示成功、失败和未执行项数。见 [结果模型与执行](../../../src/main/java/edu/files/FileChanges.java#L12) 和 [界面接收结果](../../../src/main/java/edu/files/FileManagerApp.java#L1674)。

可预期的运行时异常在回收适配器处转换。`IllegalArgumentException`、`SecurityException` 和 `UnsupportedOperationException` 发生在调用边界时，连同原始原因表示为回收结果未知。源不存在若在写入调用前已确认，则是明确失败。移动和发布保留提供者的同名冲突，其它调用后的 I/O 失败会读取源和目标属性并报告。意外的程序错误仍由任务错误路径处理。见 [LocalFiles.trash](../../../src/main/java/edu/files/LocalFiles.java#L336) 和 [移动与路径观察](../../../src/main/java/edu/files/LocalFiles.java#L416)。

“路径存在”只能反映检查时刻，不能证明文件身份或系统回收是否完成。未知项保留供用户核对，应用不自动重试。确定性的前置拒绝不记作写入。当前批次只有未知时，撤销不会退回到较早的其它批次。

真实 JavaFX 检查用三个剪切项与一个目标冲突验证了目标列表、已完成前缀、失败原因、未执行计数、剩余剪切条目及撤销记录。测试替身另覆盖了动作已经改变路径但底层抛异常的结果未知。见 [测试与变更记录](06_测试与变更记录.md)。
