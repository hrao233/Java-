## 修改位置与设计取舍

| 位置 | 修改及原因 |
| --- | --- |
| `pom.xml` | 增加 JNA 5.17.0。Java 21 可以在同一进程取得和保存句柄，通过一次原生调用提交移动。 |
| `Win32FileHandles.open`, `Handle.info`, `rename`, `Handle.close` | 集中处理 Windows DLL 映射、属性和 ID 布局、无覆盖的相对目录改名及资源释放。 |
| `NtfsFileOperations.capture`, `captureDirectory`, `verify`, `copy`, `move` | 将纯 Java 操作意图转换为 Windows 凭据，在提交期间约束源及目录对象。适配层集中承接平台条件和错误映射。 |
| `FileChanges.Selection`, `Destination`, `Receipt`, `transfer`, `rename`, `moveByHandle` | 在原批次执行器上分别保存请求快照、实际写入和逆操作条件。撤回时只复验所需身份，用户原地编辑没有失去撤回能力。 |
| `FileManagerApp.captureSelection`, `renameSelected`, `pasteInto`, `confirmCurrentPaths` | 在既有磁盘线程采集身份。JavaFX 使用凭据决定弹窗和刷新，测试可用内存 Preferences 启动应用。 |
| `LocalFiles.childNamed` | 让本地 NIO 和原生改名共用文件名单组件校验。 |

上述路径保持了阶段 2.1 的批次状态和 `LocalFiles` 入口。按目录每项提前打开句柄会将成本放进每次浏览，所以身份采集放在用户发起文件操作时。句柄用完释放，清单与阶段文档可按路径分别查看。[POM](../../../pom.xml) · [协调器](../../../src/main/java/edu/files/FileChanges.java) · [应用](../../../src/main/java/edu/files/FileManagerApp.java) · [适配层](../../../src/main/java/edu/files/NtfsFileOperations.java)

## 下一阶段候选

1. 将请求凭据和写入回执类型再收紧，给未知结果及刷新后的再次选择加独立验收。先用 `FileChanges` 的现有用例证明额外类型能减少误用，再决定是否拆出平台接口。验收应复现部分批次成功、写后未知、原名被抢占和重试失败，核对磁盘、剪切队列与撤销记录。
2. 按实际支持范围决定 NIO 降级策略。本地有稳定文件键的提供者与无键路径应分别测试。若要向用户承诺与 NTFS 相同的竞争边界，需先验证该平台能用绑定对象和目录的无覆盖提交机制。SMB、ARM64 和云文件需各自的原生与交互验证。
3. 如需恢复复制、新建的撤销，先确定是转移到可恢复位置还是进行删除。在小夹具中证明能保护复制完成后的深层新增、同大小同时间改写、符号链接和替代品后，再考虑对真实数据启用。范围、性能和回收 API 属于单独的产品决策。
